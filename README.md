# How ready is the U.S. commercial building stock for AI?

Code, assumption tables and results for the paper

> Wooyoung Jung. *How ready is the United States commercial building stock for artificial intelligence? A national
> estimate from energy codes and survey data.* arXiv:XXXX.XXXXX (identifier to be added).

## What the study estimates

An AI system that answers questions about a building, or acts on it, needs recorded data it can find: a zone
temperature with its setpoint, a whole-building interval meter, equipment status, occupancy. The study asks how much
of the U.S. commercial stock records such data, and estimates it for every building in the 2018 Commercial Buildings
Energy Consumption Survey (CBECS, 6,436 records weighted to 5.9 million buildings and 96.5 billion ft²).

Each building gets three levels of AI readiness, all on the readiness framework's question set of 76 answer levels
(Jung 2026; `atlas/canon.py`):

- **code-required**: the data streams the ASHRAE 90.1 edition in force when the building, or one of its systems, was
  built requires (`tables/C_clauses.csv`, with the edition record by state and year in `tables/V_states.csv`; row C15
  credits the submeter stream where district chilled water, steam or hot water is used; rows C16–C18 are clauses whose
  conditions or streams the survey cannot resolve and enter no estimate);
- **declared**: those plus the streams its reported controls imply (`tables/E_controls.csv`);
- **linked**: the declared streams that are recorded as time series and described well enough to be found, through a
  building automation system, a smart thermostat, an advanced meter or the 90.1-2013 monitoring clause.

The survey records neither the state nor any instrumentation point, so the unobserved layers (code edition, recording,
linkage, presence of reported controls, imputed survey answers) are multiply imputed, 200 times, and combined with
Rubin's rules over the survey's 151 jackknife replicate weights. Compliance and description are scenario dimensions;
the transfer from the reference set of 45 real building knowledge graphs to the stock is a tipping-point analysis.
Sensitivities S1–S24 vary one assumption each (S7 could not be run; there is no S4 in this release; S23, description
on BAS points as well, is reported as panel C of Table D.2; S24 credits occupancy sensing for lighting altered under
90.1-2016, clause row C06). Nothing in the analysis calls a model; every step is
deterministic given its seed.

## Reproduce

Python 3.14, Windows, macOS or Linux.

```sh
python -m venv .venv && . .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m atlas all                                  # fetch, tables, analysis, figures, ledger; M = 200
python -m atlas all --quick                          # M = 10 and a Sobol design of N = 512, to try it out
python -m pytest                                     # tests (after the fetch)
```

`python -m atlas all` runs, in order:

1. `fetch`: `scripts/fetch_data.py` downloads each third-party input from its publisher into `data/` and checks its
   SHA-256 against the hash of the file the results were computed from. A mismatch stops the run.
2. `tables`: rebuilds the input tables derived from fetched files (the reference-set census, the state energy weights,
   the advanced-meter and daily-digital-access shares by state, the linkage tables) and reports whether each equals
   the committed copy.
3. `analysis`: the multiple imputation and every scenario and sensitivity, into `results/`.
4. `figures`: every figure and table file under `figures/`.
5. `ledger`: `results/ledger.md`, every number the paper cites, by the paper's claim ID (112 IDs, C-01 … C-356).

Steps can be run alone (`python -m atlas analysis --m 200`, `python -m atlas figures`, …). `ATLAS_WORKERS` sets the
number of worker processes (default: the CPU count, at most 56). Every imputation and every Sobol design row has its
own random stream, so results do not depend on the number of workers.

Run time and memory, `python -m atlas all`:

| machine | mode | wall time | peak memory |
|---|---|---|---|
| server: AMD EPYC 9554, 128 logical cores, 256 GB, Windows Server 2025; 56 workers | M = 200 (the paper) | 63 min | about 13 GB |
| same server limited to 8 workers (a laptop-sized run) | `--quick` (M = 10, Sobol N = 512) | 14 min | about 3 GB |

Peak memory is the summed working set of the Python processes. The fetch downloads about 45 MB (2 s on the server's
connection). The longest steps at M = 200 are the sensitivities (27 min), the scenario analyses (11 min) and the gap
decomposition (10 min).

Figure 1 (method overview) is a diagram drawn in draw.io (`figures/drawio/fig_method.drawio`, exported with
`figures/drawio/export.sh`); it is not regenerated by the pipeline.
